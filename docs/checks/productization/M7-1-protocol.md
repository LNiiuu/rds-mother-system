## 1. 要回答的问题

> 在真实、连续、需求会变化的研发任务里，使用当前版本的 MARS/RDS 组织上下文，是否比常规做法
> 更省上下文、更少遗漏、更少返工，且不把成本转移到协调上？

可证伪的三组假设：

| 编号 | 假设 | 判定 |
|---|---|---|
| H1 | B 组在质量不下降的前提下，上下文成本显著低于 A | 见 §6 阈值 |
| H0 | 两组无显著差异 | 阈值不满足 |
| H2 | B 组更差（成本更高或质量更低） | 质量下降，或成本全面更高 |

`H2` 是**允许的结论**。本实验不以证明 MARS 有效为目标。

## 3. 两组定义

### 3.1 共同条件

| 项 | 设置 |
|---|---|
| 执行者 | 同一个模型（DeepSeek-V4.1-Flash），同一个会话，同一套工具权限 |
| 任务书 | 同一份 `TASK.md`，同一份 CR1 / CR2，同一时刻下发 |
| 夹具 | 同一份 `fixtures/`（只读） |
| 起始状态 | 空目录（只放任务书副本指针，不放任何骨架代码） |
| 验收 | 同一份隐藏 `acceptance.test.js`，同一 Node 版本（22.22.2） |
| 限制 | 不得引入第三方依赖；不得访问网络；不得修改 MARS 仓库 |

### 3.2 A 组：常规上下文管理

- 只允许：读任务书/CR、读写自己项目内的文件、运行 `node` / `npm test`。
- **禁止**：任何 `rds` 命令、任何 MARS 环境变量、读写 `D:\M1`。
- 上下文手段：自由重读源文件；可写一个自由格式的 `NOTES.md`（计入成本）。

### 3.3 B 组：当前 MARS/RDS

- 必须使用**真实存在**的能力（依据 [M7-0-baseline.md](M7-0-baseline.md) §4.1）：
  1. `rds init` / `init-dev`（R0 实施 + R4 审批，两个身份）
  2. `rds project register`
  3. 每个阶段的决策写入 `rds put`，由 R4 `rds review` 批准
  4. 每阶段开始前 `rds compile` 生成上下文包，并读取该包
  5. 开始时 `rds orchestrate plan`，结束时 `orchestrate feedback`
  6. 遵守角色卡 R0（实施）/ R3（测试）/ R4（审批）的**约定**（不是运行时强制）
- **禁止**：直接改 MARS 源码；用未实现的能力（`principal add`、`render-role`、MCP 客户端）。
- B 组允许读源文件；每一次重读都会被计数——这正是要测的东西。

### 3.4 顺序

**先 A 后 B**。理由与代价：

- 同会话顺序执行时，后一组天然背上前一组的历史上下文。让 B 在后，是**故意让 B 吃亏**。
- 因此若 B 在成本上仍占优，结论更可信；若 B 更差，无法区分「B 更差」与「顺序惩罚」，
  只能报「未证明价值」，不能报「B 负价值」。这一条预先写死。

## 4. 指标定义与采集

数据源统一为：WorkBuddy 会话记录 `b8b68895-….jsonl`（含每次调用的 `rawUsage` 与工具入参/输出）、
两组目录的文件快照、验收测试输出、以及执行时写入 `D:\M7-lab\logs\markers.txt` 的时间标记。

| # | 指标 | 定义 | 采集方式 |
|---|---|---|---|
| M1 | 总 Token | 组窗口内所有模型调用的 `prompt_tokens` / `completion_tokens` / `cached_tokens` 之和；另报「增量 prompt」= Σ max(0, prompt_i − prompt_{i−1})，用于剥离累积历史 | 解析 JSONL 的 `providerData.rawUsage` |
| M2 | 完成时间 | 组 START 标记到 END 标记的墙钟秒数 | 标记调用的 `timestamp`（ms） |
| M3 | 上下文重复率 | `(读取次数 − 去重文件数) / 读取次数`；读取 = `Read` 工具且带 `file_path`；另单列「任务书/CR 重读次数」 | 解析 JSONL 的 `function_call.arguments` |
| M4 | 关键需求遗漏 | 11 项需求清单（§5），每项由指定验收用例或人工检查判定；遗漏 = 未满足项数 | 验收输出 + 人工核对 |
| M5 | 返工次数 | ① 测试非零退出后修改已写过文件的次数；② 已「完成」的模块因自身缺陷被重写的次数。**不含 CR 引起的增量开发** | 调用序列人工判定，规则见 §5.2 |
| M6 | 最终质量 | 主：验收 18 例通过数；辅：自写测试通过数；再加 4 维评分（正确性/边界/结构/文档，各 0–2） | 验收输出 + 检查表 |
| M7 | 协调成本 | B：MARS 命令次数、上下文包字节、审批往返次数；A：`NOTES.md` 字节、重读字节 | JSONL + 文件大小 |
| M8 | 可追溯性 | 有命名测试或证据命令覆盖的需求项 / 11 | 需求-测试映射表 |
| M9 | 稳定性 | 非预期失败命令数（预期失败如「验证参数错误」不计）、环境错误、重试次数 | JSONL 退出码序列 |

### 4.1 Token 口径的强制说明

- `prompt_tokens` 是**每次调用的完整上下文**，包含本会话此前所有内容（含 M7-0 与本文档）。
- 因此绝对值和不可直接解释为「这一组花了多少」；必须同时看增量 prompt、completion、缓存命中。
- 结论里不得出现「节省 X% Token」这类单一数字，除非同时给出四项分解与顺序惩罚说明。
- 不采信任何估算值（如 `compile` 的 `tokens_estimated`）作为实际消耗；它只作为 B 组工具的内部口径单独列出。

### 5.2 返工判定规则（先定后数）

计入返工：
- 运行自己的测试或验收命令得到非零退出（非「故意验证错误路径」），随后修改**此前已写过的文件**；
- 同一文件在同一需求上被重写两次以上且第二次不是 CR 引起的。

不计入返工：
- CR1 / CR2 引起的增量开发；
- 为满足验收而补齐的、任务书已写明但尚未实现的项（属于未完成，计入 M4 遗漏，不重复计返工）；
- 格式整理、注释补充。

## 6. 预注册验收标准

### 6.1 实验有效性门槛（不满足则实验作废）

| # | 检查 | 要求 |
|---|---|---|
| V1 | A 组未使用 MARS | 窗口内无 `rds ` 命令、无 `MARS_` 变量 |
| V2 | B 组确实用了 MARS | 至少 3 次 `put` + 3 次 `review` + 2 次 `compile` + 1 次 `orchestrate` |
| V3 | 同题同尺 | 两组使用同一 spec/acceptance 哈希（§2.2） |
| V4 | 未改产品 | `D:\M1` 除新增 `docs/` 外无改动；`git status` 与 M7-0 一致 |
| V5 | 验收可跑 | 两组都用 `ARM_DIR=<dir> node --test acceptance.test.js` 跑同一份文件 |

### 6.2 质量门槛

- 两组都必须能启动 CLI 并通过至少 1 个用例，否则该组记为「未交付」。
- 质量比较以验收通过数为准；**不允许**因为某组「设计更漂亮」而调整通过数。

### 6.3 「MARS 有实际价值」的判定阈值（全部满足）

1. **质量不下降**：B 的验收通过数 ≥ A；
2. **至少一项成本显著更优**：增量 prompt ≤ A 的 75%，或重复读取率 ≤ A 的 50%，或遗漏数 < A；
3. **协调成本未吞掉收益**：B 的协调字节（MARS 命令 + 包读取）< 其相对 A 节省的上下文字节。

若质量更好但成本更高 → 结论写「质量有效、成本不成立」，不算整体价值成立。
若质量更差 → 结论写「负价值」，并给出具体失败点。

> 阈值在实验前写定，实验后不得调整。样本量 N=1/组，不做统计显著性推断。

## 7. 混杂因素（预先声明，报告必须逐条回应）

| # | 混杂 | 影响 | 处理 |
|---|---|---|---|
| C1 | 同会话顺序执行 | 后一组背更多历史 | 先 A 后 B，故意不利于 B；同时报增量 prompt |
| C2 | 执行者即实验者 | 可能存在期望偏差 | 预注册指标与阈值；B 组按固定命令清单执行；质量用隐藏测试 |
| C3 | 无语义盲评 | 质量评分非独立 | 主指标用客观测试；4 维评分标注为「自评，仅参考」 |
| C4 | 单样本 | 不能外推 | 报告明确写「N=1，方向性证据」 |
| C5 | 上下文压缩 | 中途压缩会改变成本曲线 | 记录是否发生及发生点 |
| C6 | 工具可用性 | B 的 CLI 有学习成本 | 成本计入 B，不豁免 |
| C7 | 我已知假设 | 可能不自觉「演」 | 两组都按清单机械执行；A 组不得引用 MARS 术语 |

## 9. 中止条件

- 预注册文件哈希变化 → 作废重跑；
- 验收测试自身有 bug（非被测代码问题）→ 修复测试，**两组都重跑**，并在报告记录；
- 上下文压缩发生在某一组中途 → 记录时间点，结论中标注该组成本曲线不可比；
- 发现必须修改 MARS 才能继续 → 停止，先向用户说明原因、影响与替代方案，不擅自改。
