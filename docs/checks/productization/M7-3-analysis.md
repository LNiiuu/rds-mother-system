# M7-3 结果分析

**日期**：2026-11-12（+08:00）
**输入**：[M7-2-experiment-record.md](M7-2-experiment-record.md) 的原始数据；方案与阈值见 [M7-1-protocol.md](M7-1-protocol.md)。
**结论先行**：**H1（MARS 更有价值）不成立；判定为 H0「未证明价值」，且协调成本有可测的增加。**

### 1.1 关于 M1 的口径

prompt tokens 不能直接比：A 3.62M / B 5.45M，是因为 B 在 A 之后执行，窗口里已经背着 A 的完整记录。
可比的量是「每次调用新增的上下文」与「模型实际产出」：

```
A：增量 prompt 20 556 + completion 14 220 = 34 776
B：增量 prompt 22 055 + completion 12 452 = 34 507
```

**差 −269 tokens，0.8%。** 在一个 34k 量级的边际成本上，这个差值没有解释力，只能算持平。

B 的 completion 更少（−12%），因为它少写了一个模块（4 文件 449 行 vs 5 文件 479 行）；
B 的增量 prompt 更多（+7.3%），因为要读 3 份上下文包、看 MARS 的 JSON 输出。
两者相互抵消。

## 2. 协调成本：增加在哪里

| 项 | 数值 |
|---|---|
| MARS 审计动作 | **33**（propose 8、review 8、compile 3、list 12、register 1、plan 1） |
| 上下文包总量 | **31 787 B**（3 份，10.1 / 10.6 / 11.1 KB） |
| 工具输出字节 | 31 164 B（A 为 14 267 B，**+118%**） |
| 模型调用 | 20 次（A 17 次，**+18%**） |

### 2.1 一次决策的真实往返

写一条决策要两步：`put`（R0）→ `review`（R4）。8 条决策 = **16 次调用**，全部是人工逐条执行。
这 8 条决策的内容**全部来自任务书原文**，本质上是把已经读过的规范再抄一遍，
既没有产生新信息，也没有减少后续读取——因为包的 `sec_task` 不含任务正文，B 仍然读了 `TASK.md`。

### 2.2 上下文包的结构开销

`packet-v1.json` 的实测：

| 项 | 值 |
|---|---|
| 文件大小 | 10 105 B |
| 工具自报内容量 | 240 tokens |
| 字节 / token | ≈ 42 : 1 |
| 内容重复 | 同一段 content 在 `packet.sections` 与 `budget.sections` 各出现一次，`manifest.entries` 再列一遍元数据 |

也就是说，读完一个「240 tokens 的上下文包」，实际要吞下 10 KB 的 JSON。
这不是打包，这是把同一份内容印刷了三遍。

### 2.3 收益侧：只有一处可测的减少

B 读了 **2 个文件**（packet-v1、TASK.md），A 读了 **3 个**（TASK、CR1、CR2）。
B 在 CR1/CR2 阶段确实没有重读变更文件——但这不能算节省：

- 两份 CR 合计 66 行、约 1.7 KB；
- B 为此付出了 3 次 `compile` + 3 次包内决策打印，仅包文件就是 31.8 KB。

**用 31.8 KB 的机械产物，替代了 1.7 KB 的原文阅读。**

## 3. 逐条回答协议里的问题

### 3.1 是否增加了 Agent 协调成本？

**是，显著增加。** 33 次审计动作、20 次模型调用（+18%）、工具输出翻倍（+118%）。
增加的部分几乎全是**流程开销**，不是任务本身需要的工作。

### 3.2 是否出现上下文丢失或错误路由？

**上下文丢失：存在结构性风险。**
`packet.sec_task` 的内容是字面量「任务: XSUM-1」——编译器只拿到任务 ID，没拿到任务正文。
如果执行者真的「只读包、不读源文件」，会丢掉全部字段规则、输出格式、退出码定义。
B 组之所以没出事，是因为它**额外读了 `TASK.md`**，也就是绕过了这个缺陷。

**错误路由：存在，可复现。**
同一个任务，换一种措辞调用 `orchestrate plan`：

| objective | 分类 | 派发角色 |
|---|---|---|
| 「实现账单聚合 CLI 并补测试」 | `verification` | R3 |
| 「实现交易流水聚合 CLI xsum，含 CSV/JSONL 解析、去重、汇率换算与聚合输出」 | `implementation` | R2, R3 |

关键词规则对措辞敏感。真实使用中，任务描述由人写，分类就会漂移。

### 3.3 是否存在重复读取、重复总结、无效压缩？

- **重复读取：0。** 两组都没有重复读同一文件。单会话 + 强记忆让这个指标失去区分度。
- **重复总结：存在，且是 B 的主要浪费。** 6 条决策是任务书的摘要，CR1/CR2 又各压成一句；
  这些摘要与原文并存，读包时两者都要过一遍。
- **无效压缩：存在。** `sec_decisions` 把 CR2 的换算规则压成一行，丢掉了「`S == T` 也要走舍入」
  这类边界；包不能替代原文，只能当索引。

### 3.4 Token 节省是否被额外调用成本抵消？

**没有节省可被抵消——节省本身就是 0。**
边际 token 34 776 vs 34 507，差 0.8%；调用次数与输出字节都是 B 更高。
按协议 §6.3 的第 2 条（至少一项成本 ≤ A 的 75% 或重复率 ≤ 50%），**不满足**。

### 3.5 R0–R7 的角色划分是否真正有效？

**在本实验中未被检验，不能声称有效。**

- 代码层只强制两种角色：R0（可写/可编译）与 R4（可审批）。这一点**真实生效**：
  R4 执行 `compile` 被 `AUTHZ_DENIED ROLE_DENIED` 拒绝。
- R1–R3、R5–R7 只存在于 `core/roles/*.md`，没有运行时约束，也没有独立 Agent 实例。
- `orchestrate plan` 派了 R2、R3，但整个任务由同一个执行者完成，**没有发生真正的多角色协作**。

所以：**「职责分离」被验证了（R0 写、R4 批）；「多角色协作提升质量」没有被验证。**

### 3.6 哪些能力有效，哪些没有体现价值？

| 能力 | 状态 | 证据 |
|---|---|---|
| 记忆写入 / 审批 / 检索 | **功能有效** | 8 条写入、8 条审批、检索命中；自审被拒 |
| 权限与角色边界 | **功能有效** | R4 编译被拒；R0 可写 |
| 上下文包编译（预算、missing、prohibited） | **机制有效，载体失败** | 预算 240/4000 生效；但包不含任务正文、体积膨胀 42 倍 |
| 编排计划 / 运行记录 / 反馈 | **记录有效，决策不可靠** | run 状态、预算、feedback 都能落库；分类随措辞漂移 |
| 审计 | **有效** | 33 条动作可回溯到主体与时间 |
| 角色卡 / 工作流 / 证据分级 | **仅为约定** | 无代码强制，本实验未产生可测收益 |
| MCP 接入 / render-role | **未参与** | 默认禁用 / 未入库 |

### 3.7 当前系统最主要的瓶颈

按影响排序：

1. **上下文包不能自足**：不含任务正文，执行者必须回到源文件。这一条直接否定了「编译一次、少读原文」的核心承诺。
2. **包的载体效率极低**：10 KB 承载 240 tokens，内容重复三遍。读包比读原文更贵。
3. **写入/审批是逐条人工往返**：8 条决策 16 次调用，没有批量入口，也没有从文件导入。
4. **没有真实的成本账本**：`orchestrate feedback --tokens` 要人手工填；系统不知道自己省没省。
5. **身份管理脆弱**：`init-dev` 覆盖式写入，一次误操作就丢掉全部 token（M7-0 已实测）。

## 4. 对混杂因素的回应（协议 §7）

| # | 混杂 | 实际影响 | 是否影响结论 |
|---|---|---|---|
| C1 | 同会话顺序执行 | B 的 prompt 总量必然更大；已改用增量口径 | 已消除 |
| C2 | 执行者即实验者 | 预注册 + 固定命令清单 + 隐藏测试 | 部分缓解 |
| C3 | 无独立盲评 | 质量主指标是客观测试（19/19 双方） | 不影响质量结论 |
| C4 | 单样本 | 不能外推 | 结论限定为「本任务、本执行者」 |
| C5 | 上下文压缩 | 窗口内未发生压缩 | 不影响 |
| C6 | B 有学习成本 | 计入 B，未豁免 | 对 B 不利，结论偏保守 |
| **C7** | **执行者预知全部 CR** | **A/B 都提前预留了扩展点，两个 CR 阶段零源码改动** | **使「记忆收益」无法被测出** |
| **C8** | **学习效应** | **B 是第二次做同一任务，墙钟 −76% 主要来自熟练度** | **B 的速度优势不可信** |

C7 与 C8 是本次设计的两个硬伤，方向相反：C7 压低 B 的收益，C8 抬高 B 的速度。
因此本报告**不使用速度作为价值证据**，也不把「CR 阶段零改动」算作 MARS 的功劳。

## 5. 判定

按协议 §6.3 的三条阈值：

| 条件 | 结果 |
|---|---|
| 质量不下降（B ≥ A） | **满足**（19/19 = 19/19） |
| 至少一项成本显著更优 | **不满足**（增量 prompt +7.3%、重复率持平、遗漏持平） |
| 协调成本未吞掉收益 | **不满足**（收益为 0，协调 +33 次动作） |

**结论：H1 不成立。判定 H0「未证明价值」。**

不判 H2（负价值），理由：质量完全持平、边际 token 持平；
B 的额外开销没有造成交付质量下降，只是没有带来任何可测收益。
更准确的说法是：**在当前形态下，MARS 是一套「能跑通、但不省钱」的流程层。**
