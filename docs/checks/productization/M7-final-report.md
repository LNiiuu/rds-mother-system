# M7 最终报告：真实长任务验证与产品价值评估

**日期**：2026-11-12（+08:00）
**范围**：M7-0 基线 → M7-1 方案 → M7-2 实验 → M7-3 分析 → 本报告
**阶段判定**：**`COMPLETED`**（实验按预注册完成、证据完整）
**产品判定**：**`NOT SUPPORTED`**（本实验未证明 MARS 在真实长任务中有可测价值）

> 两个判定是两件事：阶段做完了，不代表假设成立。

---

## 1. 一句话结论

在同一个真实任务、同一模型、同一工具、同一把隐藏验收尺子下，
**用 MARS 的一组与不用的那组，交付质量完全相同（19/19），边际 token 基本相同（34 507 vs 34 776），
而 MARS 组多付出了 33 次流程动作与 118% 的工具输出。**

---

## 2. 六个问题的回答

### 2.1 MARS 是否在真实长任务中体现出实际价值？

**没有。** 按预注册阈值：

| 条件 | 要求 | 实测 | 结果 |
|---|---|---|---|
| 质量不下降 | B ≥ A | 19/19 = 19/19 | ✅ |
| 至少一项成本显著更优 | 增量 prompt ≤ 75% A，或重复率 ≤ 50%，或遗漏更少 | +7.3% / 持平 / 持平 | ❌ |
| 协调成本未吞掉收益 | 协调 < 节省 | 节省 0，协调 +33 动作 | ❌ |

判定 **H0：未证明价值**。不判负价值，因为质量与边际 token 都没变差。

### 2.2 哪些能力已经被实验验证？

**功能层面（能跑、有正确行为）**：

| 能力 | 验证方式 |
|---|---|
| 记忆写入 / 审批 / 检索 | 8 条决策写入、8 条 R4 审批、检索命中 |
| 双人审批（不能自审） | 同身份审批被拒；R4 审批成功 |
| 角色权限边界 | R4 执行 `compile` 被 `AUTHZ_DENIED ROLE_DENIED` |
| 上下文包预算与缺项提示 | `tokens=240/4000`；`missing` 给出 1 条 blocking |
| 编排计划 / 运行 / 反馈 | plan、start、feedback、status 全部落库，预算 34 507/200 000 |
| 审计可回溯 | 33 条动作带主体与时间戳 |
| 身份与项目初始化 | init / init-dev / project register 可用 |

**价值层面（是否更省、更快、更好）**：**一个都没有被验证。**
质量持平、token 持平、速度优势不可归因（学习效应）、协调成本更高。

### 2.3 哪些能力仍然只是理论设计？

| 能力 | 实际状态 |
|---|---|
| R0–R7 多角色协作 | 代码只强制 R0/R4 两种权限；R1–R3、R5–R7 是 Markdown 约定 |
| WF1–WF4 工作流 | 纯文档，无运行时校验 |
| 证据分级 E1–E4 | 纯文档 |
| 「上下文包替代原文阅读」 | **本实验证伪**：包不含任务正文，仍必须读原文 |
| MCP 客户端接入 | 代码存在、默认禁用，本实验未接 |
| `render-role` 角色包渲染 | 只有未入库的 `.ps1`，不计入产品能力 |
| 跨 Agent / 跨会话协作 | 未验证 |

### 2.4 当前架构是否需要调整？

**需要，而且不是加功能，是修载体。**

三个必须修的结构问题（按影响排序）：

1. **上下文包不自足**：`sec_task` 只有「任务: XSUM-1」。编译器没有任务正文的入口，
   这使「编译一次、少读源文件」的核心承诺不成立。
2. **包体积是内容的 42 倍**：10 105 B 承载 240 tokens，同一段内容在 `packet` / `budget` 里各印一遍，
   `manifest` 再列一遍。读包比读原文更贵。
3. **写入/审批逐条往返**：8 条决策 16 次调用，无批量入口、无文件导入。

### 2.5 是否值得进入下一阶段开发？

**有条件值得，但只值得做「降成本」，不值得做「加能力」。**

- 如果下一阶段继续加角色、加工作流、加 MCP 工具面：**不建议**。本实验没有证据表明这些会带来收益，
  而每加一层都会增加协调成本。
- 如果下一阶段只做三个降成本改造，并用一次**交叉平衡的新实验**验证：**建议做**。

判断依据：当前瓶颈是「工具的输出比它替代的东西更贵」，这是工程问题，不是能力问题，可修。

### 2.6 下一阶段应该优先解决什么问题？

| 优先级 | 问题 | 具体动作 | 验收标准 |
|---|---|---|---|
| **P0-1** | 包不自足 | 增加任务正文入口（`rds task put --file` 或 `compile --task-file`），`sec_task` 必须含正文 | 只读包能复述全部字段规则与输出格式；不读原文也能通过验收 |
| **P0-2** | 包体积膨胀 | `compile --format md`（或 `--sections-only`），去掉 `budget`/`manifest` 重复；同内容只出现一次 | 240 tokens 的包 ≤ 2 KB；读包字节 < 读原文字节 |
| **P0-3** | 逐条往返 | `put --from <file>` 批量导入 + `review --batch` | 8 条决策 ≤ 2 次调用 |
| P1-1 | 无成本账本 | `orchestrate feedback` 自动从会话账本取数；`rds run report` 输出边际 token | 不手工填 tokens，能对比两次运行 |
| P1-2 | 身份覆盖 | `init-dev --add` 追加入口 | 追加第二个 principal 不破坏第一个 token |
| P1-3 | 分类漂移 | 记录分类依据（命中关键词），允许 `--class` 覆盖 | 同一任务换措辞，分类可由人锁定 |
| P2-1 | 角色是纸面约定 | 要么把 R1–R7 做成可执行检查表，要么在文档里明确「只是约定」 | 文档与代码一致 |
| P2-2 | 多 Agent 未验证 | 用两个独立执行者做一次真实交接 | 有交接产物与质量对比 |

## 3. 这次实验本身的局限（必须先说）

| 局限 | 后果 |
|---|---|
| **N = 1 / 组** | 不能做统计推断，结论只对「这个任务 + 这个执行者」成立 |
| **执行者预知全部 CR** | 两个变更阶段零源码改动，**记忆收益根本没被考到** |
| **学习效应** | B 是第二次做同一任务，墙钟快 76% 不可信 |
| **同会话顺序执行** | 已用增量口径剥离，但缓存命中率仍不可比 |
| **无独立盲评** | 质量靠客观测试，主观评分未采用 |
| **任务偏小** | 449–479 行、20 分钟量级，不是「多天」的长任务 |

**这些局限不改变「本次没有测到价值」这个事实，但限制了它的外推范围。**
要证明 MARS 有价值，需要：新执行者（不知道 CR）+ 交叉顺序（A→B 与 B→A 各一次）+ N ≥ 3 个任务。
