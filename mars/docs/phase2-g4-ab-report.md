# Phase 2 · G4 Token 与质量 A/B 对照报告

> 目的：在同一模型、同一任务、同一输出要求下，对比“原有上下文传递方式”（基线）与“MARS 角色专属上下文”（实验）的成本与质量。
> 结论性质：**受控小样本**（R1 单角色、单任务、每组 3 次），只证明方向与机制，不构成规模结论。Token 为 DSH 会话原始 `usage` 数据，不是 provider 账单。

## 1. 实验设计

| 项 | 基线（A） | 实验（B） |
|---|---|---|
| 上下文来源 | 角色说明 + 全部 8 条 approved 记忆 + 任务卡 | `compileContext` 生成的 R1 packet（5 段） |
| 载荷估算 | 1,306 字符 / 459 tokens（估算器） | 1,115 字符 / 392 tokens（估算器，packet 自报 366） |
| 模型/参数 | 同一会话模型与默认参数 | 同左 |
| 任务 | 输出 JSON：task_id、3 条决策 ID、2 条禁止事项、1 条 DB 事实 | 同左 |
| 约束 | 禁止调用工具/读文件；每组 3 次 | 同左 |
| 计量 | 会话 `assistant/message.data.usage`（ledger `parseSession`） | 同左 |

## 3. 结论

1. **质量**：在本任务上，角色专属上下文显著减少“把知识当决策、把决策当禁止事项”的结构性错误（8/15 → 15/15）；机制有效。
2. **Token**：未见显著下降（−1.65%，在冷启动噪声内）；根因是上下文载荷（约 0.4K tokens）远小于系统提示与工具定义开销。要看到成本差异，需在长会话、多任务、累积记忆规模下复测。
3. **不可外推**：单角色（R1）、单任务、每组 3 次、无工具调用；R2/R3/R4 与工具型任务需在 Phase 2.1 补测。
